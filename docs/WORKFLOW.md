# Как мы работаем вдвоём (и с Claude)

Правила для двоих, кто не профессиональные программисты. Цель простая: **рабочий сайт не ломается**,
а любое изменение сначала проверяется на тестовом адресе с тестовой базой.

Если правило мешает работе, не нарушайте его молча: договоритесь в чате и поправьте этот файл.

## 1. Три среды

| Среда | Код | База данных (Supabase) | Где смотреть |
|---|---|---|---|
| **Рабочая** | ветка `main` | рабочий проект («Brubusenok's Project») | https://mafia-league-staging.vercel.app |
| **Тестовая** | любая ветка или pull request | тестовый проект `mafia-league-preview` | свой адрес у каждой сборки в Vercel |
| **Локальная** | у каждого на компьютере | та, что записана в `.env.local` | `http://localhost:3000` |

Главное: **тестовую базу можно ломать, рабочую — нет.** Тестовую можно в любой момент сбросить файлом
`supabase/reset-preview-only.sql` и загрузить заново (раздел 5).

Значения `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` публичные. Секретный ключ
(`secret` / `service_role`) и пароль базы **нигде не хранить в коде, не вставлять в Vercel, не присылать в чат**.

## 2. Как менять код

1. **В `main` никто не пушит напрямую.** Любое изменение: новая ветка от свежего `main`, коммиты, pull request.
2. Ветки короткие: сделали одно, проверили, влили. Чем дольше живёт ветка, тем больше конфликтов.
3. Перед началом работы всегда берите свежий `main`.
4. Не правьте одни и те же файлы вдвоём одновременно. Перед большой работой напишите второму, какие
   разделы затронете (например: «беру рейтинг и миграции» / «беру страницы и дизайн»).
5. Один pull request решает одну задачу. Большие pull request (десятки файлов, миграция базы и интерфейс сразу)
   делите на части. Если делить нельзя, предупредите заранее.
6. Влить pull request можно только после того, как **второй человек сказал «да»**. Автор pull request сам себе «да» не говорит.

## 3. Проверка перед слиянием

Перед просьбой «влей» должно быть выполнено всё из списка (он же в шаблоне pull request):

- `npm run lint` и `npm run build` проходят без ошибок;
- изменение проверено **на тестовом адресе** (или локально на тестовой базе), а не только «собралось»;
- страницы открываются на телефоне (ширина 375 px) без горизонтальной прокрутки;
- если есть миграция базы: она уже применена на тестовой базе (раздел 5).

## 4. Как выкладывать на рабочий сайт

Сейчас Vercel собирает **форк** `Brubusenok/mafia-league-staging`, а не основной репозиторий.
Поэтому после слияния pull request:

```bash
git checkout main && git pull origin main && git push fork main
```

Через 1–2 минуты в Vercel (Deployments) появится новая сборка. Дождитесь статуса **Ready** и откройте сайт.
Когда Vercel подключат к основному репозиторию, этот шаг исчезнет (см. раздел 8).

**Тестовый адрес для ветки.** Автоматически он появляется не всегда. Создать вручную: Vercel → Deployments →
меню «…» справа вверху → **Create Deployment** → выбрать ветку → **Create Preview Deployment**.
Ветка должна быть в форке: `git push fork <ветка>`.

## 5. Правила для базы данных (самое опасное место)

Рабочая база — это настоящие данные клуба. Ошибка здесь не откатывается кнопкой.

1. **Запрос, который меняет рабочую базу** (любой SQL в SQL Editor рабочего проекта, любая миграция), выполняется
   только после того, как **оба** написали «да» в чате, и с указанием, какой именно файл запускается.
2. **Сначала на тестовой базе.** Любую новую миграцию запускают на тестовой, проверяют сайт, и только потом думают о рабочей.
3. **Миграция не должна ломать код, который сейчас на рабочем сайте.** Если ломает (удаляет колонку, меняет
   функцию, от которой зависит старый код), код и миграцию выкладывают в один заход по плану из раздела 6.
4. Файлы миграций лежат в `supabase/migrations/` и запускаются **по порядку номеров**. Номер нельзя менять и
   нельзя вставлять новую миграцию перед уже запущенными на рабочей базе.
5. Перед миграцией на рабочей базе: **копия данных** (Database → Backups, а если копий нет на тарифе, выгрузка
   таблиц из Table Editor в CSV) и метка на последней рабочей версии кода (раздел 6, шаг 2).
6. Для тестовой базы с нуля: все файлы `supabase/migrations/*.sql` по порядку, затем **только** `supabase/preview-seed.sql`
   (не вместе с `seed.sql`). Сброс перед этим: `supabase/reset-preview-only.sql`. Он сам остановится, если в базе есть игроки, но всё равно
   убедитесь, что открыт именно **тестовый** проект. Запускать его на рабочей базе нельзя.
7. Пароли и ключи не вставляются в миграции.

## 6. «Окно выкладки»: когда меняется и код, и база

Так выкладывают всё, что включает миграцию рабочей базы (например, pull request League Core). Назначьте время,
когда оба на связи и сайт можно ненадолго потревожить.

1. **Подготовка.** Pull request проверен на тестовом адресе под администратором; оба согласны.
2. **Страховка.** Поставьте метку на текущую рабочую версию и сделайте копию данных рабочей базы:
   ```bash
   git tag -a stable-<дата> <коммит-main> -m "Рабочая версия перед выкладкой"
   git push origin stable-<дата>
   ```
   Метка `stable-before-merge` уже стоит на коммите `c081456` (до League Core).
3. **Миграция.** Выполнить SQL-файл(ы) на рабочей базе (SQL Editor → Run), строго по порядку.
4. **Код.** Сразу влить pull request и отправить `main` в форк (раздел 4).
5. **Проверка.** После статуса **Ready** открыть рабочий сайт: главная, рейтинг, игроки, история, вход,
   админка → ввод и сохранение партии.
6. **Если что-то сломалось.** Остановиться, сообщить второму. Код откатывается на метку:
   ```bash
   git checkout main && git revert -m 1 <коммит-слияния> && git push origin main && git push fork main
   ```
   Данные базы откатываются только из копии, поэтому копия обязательна. Миграции откатывать вручную без второго человека не нужно.

## 7. Что решаем вместе, а не в одиночку

- Формула рейтинга и что в него входит (Short9, ничьи, технические результаты).
- Языки сайта (сейчас основной русский; украинский переведён частично).
- Удаление данных на рабочей базе, смена структуры базы, правила доступа (RLS).
- Изменение этого файла.

## 8. Что ещё предстоит (автоматизация)

- Подключить Vercel к основному репозиторию `manarisqa/mafia-league-staging`: тогда каждый pull request сам получает
  тестовый адрес, а слияние в `main` само обновляет рабочий сайт. Ручной `git push fork main` и форк не понадобятся.
  В Vercel: Production — ключи рабочей Supabase, Preview — ключи тестовой.
- Включить защиту `main` на GitHub (Settings → Branches): слияние только через pull request и только при пройденной проверке.
- Сделать так, чтобы **все** тестовые сборки (не только одна ветка) ходили в тестовую базу.

## 9. Шпаргалка

| Что нужно | Как |
|---|---|
| Начать новую задачу | `git checkout main && git pull origin main && git checkout -b feat/<название>` |
| Отправить ветку | `git push -u origin feat/<название>` и открыть pull request |
| Обновить рабочий сайт после слияния | `git checkout main && git pull origin main && git push fork main` |
| Вернуться к последней рабочей версии | `git checkout stable-before-merge` (только посмотреть код; откат делает `git revert`) |
| Проверить локально | `npm install`, `npm run dev`, затем `npm run lint` и `npm run build` |
| Кому писать, если сломалось | второму человеку в чате, сразу, с текстом ошибки целиком |
